# Проверка полноты FAT / I/O-протокола АСУ ТП — CSV QA

Публичный **офлайн-инструмент** DLV Automation для инженеров ПЛК, SCADA, КИПиА и ПНР. Помогает проверить, насколько полно заполнен протокол I/O-тестов перед ревью и передачей: отсутствующие исходные данные, повторяющиеся ID, результаты PASS без подтверждения и FAIL без замечания.

Это **проверка документа**, не оборудование, не программа испытаний и не допуск к ПНР. Скрипт **не соединяется с ПЛК**, не посылает Modbus/PROFINET-запросы, не читает секреты и не отправляет данные в сеть. Результаты нельзя использовать как подтверждение безопасности, корректности защит или санитарной валидации.

## Формат

Файл создаётся бесплатно на странице [FAT, I/O-тесты и SAT — шаблон CSV](https://dlvautomation.ru/blog/fat-io-testy-pnr-asu-tp/). Шаблон использует **UTF-8 с BOM** и **разделитель точка с запятой**. Обязательные названия колонок: `ID`, `Участок`, `Позиция`, `Тип I/O`, `Адрес ПЛК`, `Начальные условия`, `Проверочное воздействие`, `Ожидается в ПЛК`, `Ожидается на HMI/SCADA`, `Фактически`, `Статус`, `Замечание`, `Ответственный`, `Версия ПО`, `Дата`.

Типы сигналов: `DI`, `DO`, `AI`, `AO`, `COM`. Статусы: `PASS` (доказанный результат), `FAIL` (с замечанием), `BLOCKED` (невозможно проверить), `NOT_RUN` (ещё не выполнялось). Слова и статусы нужно согласовать в рабочей процедуре организации — скрипт не устанавливает регламент испытаний.

Строки с ID `ПРИМЕР-` из шаблона не учитываются как подтверждённые проверки; пустые `TEST-01`, `TEST-02` и т. п. тоже игнорируются. После заполнения `TEST-01` становится рабочей строкой.

## Как использовать

Нужен Python 3.10+ без сторонних пакетов. Из корня репозитория:

```bash
python3 examples/fat-io-csv-review/check_fat_csv.py DLV_FAT_IO_test_protocol_template.csv
python3 examples/fat-io-csv-review/check_fat_csv.py --strict DLV_FAT_IO_test_protocol_template.csv
python3 examples/fat-io-csv-review/check_fat_csv.py --json DLV_FAT_IO_test_protocol_template.csv
```

Код возврата: `0` — формат корректен и при выбранном режиме критичных замечаний нет; `1` — в строгом режиме есть предупреждения о неполноте; `2` — ошибка, например дубли ID, недопустимый тип/статус, неподтверждённый PASS или пустой реальный протокол в строгом режиме.

Для `PASS` нужны фактический результат, ответственный, версия ПО и дата. Для `FAIL` дополнительно обязательно замечание. Наличие заполненных полей **не означает**, что проверка была реально проведена.

Для проверки кода и изолированных тестовых сценариев:

```bash
python3 -m unittest discover -s examples/fat-io-csv-review -p 'test_*.py'
```

## Где применить

- Первичная проверка полноты протокола перед техническим ревью и согласованием FAT/SAT.
- Контроль статусов I/O-тестов по типам сигналов и незакрытым документальным вопросам.
- Выгрузка `--json` в локальные отчёты или внутренний CI без передачи заводских данных в внешние сервисы.

Отдельно смотрите [калькулятор 4–20 мА и raw ПЛК](https://dlvautomation.ru/blog/4-20ma-plk-kalkulyator/) и [программную пусконаладку АСУ ТП](https://dlvautomation.ru/puskonaladka-programmnogo-obespecheniya-asu-tp/). Используйте фактическую документацию оборудования, процедуру допуска и действующие нормы; иллюстративные строки шаблона не являются схемой реальной установки.
