# DLV Timeweb HTTPS: разграничение DNS / TCP / TLS / HTTP / публикации

**Дата:** 03.11.2026. Публичная техническая памятка; без паролей и данных заказчиков.

## Почему это важно для SEO

Google Search Console на последней полной проверке показывала **28/49 PASS, 21 NEUTRAL**. Внешние GitHub Runner-проверки временами завершались тайм-аутами на `/robots.txt`, `/sitemap.xml` и `/dlv-deploy-revision.txt`, хотя между ними Timeweb действительно возвращал HTTP 200, 49 URL и корректный опубликованный SHA. Отдельные неиндексируемые коммерческие страницы не означают доказанную блокировку робота поисковой системы.

**Не менять DNS/хостинг по одному тайм-ауту.** Проверить логи Timeweb, официальную GSC Crawl Stats и результаты нескольких независимых внешних проб.

## Новая диагностическая ступень GitHub Actions

`scripts/probe_production_https.py` выполняется **до** SEO-монитора и сохраняет `seo-reports/https-layer.json` в артефакте `dlv-public-site-report`, даже если основной аудит сайта завершился неуспешно.

Отдельные поля:

- `dns`: какие IPv4/IPv6-адреса вернул резолвер GitHub Runner;
- `tcp` и `tcp_ms`: удалось ли открыть прямое соединение на порт 443;
- `tls` и `tls_ms`: прошла ли проверка сертификата, имени хоста и TLS-рукопожатие с SNI;
- `http_status` и `response_ms`: вернулся ли HTTP-статус на GET `/robots.txt` и файл ревизии;
- `proxy_env_present`: только **наличие**, без значений, потенциальных прокси-переменных среды.

Проба делает один короткий запрос на каждую пару адрес/путь, не выполняет записи, не использует учетные данные и не проверяет чужие сайты. Отсутствие ответа GitHub Runner **не доказывает**, что Googlebot или ЯндексБот недоступны.

## Интерпретация с возможным следующим действием

| Симптом | Уточняем | Что проверить у хостера |
| --- | --- | --- |
| `dns_resolution` | DNS в среде проверки, авторитетные NS, A/AAAA | Логи DNS или временный сбой резолвера, не менять A без причины |
| `tcp=timeout` при наличии IP | Путь до 443, фильтрацию по IP и географии, блокировки | L3/L4, анти-DDoS, iptables/ACL, SYN-трафик в момент события |
| `tls=timeout` или `tls_certificate` | SNI, сертификат и завершение HTTPS | nginx frontend TLS, сертификаты, время рукопожатия |
| `tls=ok`, `http=timeout` | HTTP/1.1 обработка после TLS | nginx/access/error, rate limits, защитные правила по User-Agent |
| HTTP 200, но SHA Timeweb старый | DNS/HTTP работают, код сайта неактуален | Cron, lock, git fetch/HTTPS 443, rsync, `dlv-deploy-revision.txt` |
| HTTP 200 и SHA совпадает, но GSC NEUTRAL | Проблема может быть не техническая | GSC URL Inspection, last crawl, canonical, дубли, внутренние ссылки и ценность страницы |

Для проверки доступности **именно Googlebot** нужны данные Google Search Console «Статистика сканирования», «Проверить опубликованную страницу» и серверные access/error-логи. Случайные сторонние User-Agent не являются подлинным Googlebot.

## Зачем это SEO

При повторной ошибке `robots.txt` поисковый робот может отложить сканирование; это описано в [Google Search Console Help](https://support.google.com/webmasters/answer/35164). Цель диагностики — подтверждённая причина и устойчивый обход, а не отчёт ради отчёта.

Измеримый результат после устранения проблемы: стабильные внешние проверки, опубликованный SHA=main, проверка приоритетных коммерческих URL и дальнейшие изменения **кликов/показов** по непересекающимся 7-дневным периодам Google.
