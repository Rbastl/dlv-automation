# DLV Automation → Timeweb: автоматическая публикация без FTP

**Важно, 04.11.2026:** этот файл описывает **историческую первичную настройку 13 октября**, когда DNS ещё не был перенесён. Сейчас `https://dlvautomation.ru/` работает на **Timeweb**, а GitHub `main` — источник кода. Netlify и GitHub Pages — не production. **Не повторять инструкции переключения DNS, создания Cron и смены хостинга.** Актуальный порядок контроля см. в [SEO_AUTOMATION_SETUP.md](SEO_AUTOMATION_SETUP.md) и открытой [P0-задаче #43](https://github.com/Rbastl/dlv-automation/issues/43).

Не создавать второй Cron наугад.
- По тикету Timeweb **№12945785** требуется верификация владельца по официальному каналу, затем запрос логов сетевого фронтенда/TCP/443, nginx/WAF/ACL и Cron. Для статических `robots.txt`/`sitemap.xml` Apache access_log может быть недостаточен (часть запросов обслуживает nginx).

## Почему отказались от FTPS

После сохранения трёх GitHub Secrets проверка GitHub Actions FTPS закончилась ошибкой. В исходном режиме Node.js пытался IPv4+IPv6 и попадал в тайм-аут. Принудительный IPv4 установил TCP-соединение, но FTP-сервер ответил кодом `530 Please login with USER and PASS` при попытке установить защищённую сессию. Timeweb в своей документации допускает обычный FTP, но мы **не будем передавать пароль в открытом виде**. SFTP дополнительному ограниченному FTP-пользователю Timeweb не предоставляет: по документации SFTP разрешён только основному пользователю аккаунта; секреты основного владельца в GitHub хранить не следует.

Поэтому выбрана схема **Timeweb самостоятельно забирает публичные файлы из GitHub по HTTPS (порт 443)**. Пароли не нужны, API-токены не нужны, ключи администратора на GitHub Actions не передаются.

## Подготовленный скрипт

`scripts/timeweb_sync_from_github.sh`

- Источник: публичный репозиторий `Rbastl/dlv-automation`, ветка `main`.
- Защищённый `git clone/pull` через HTTPS; если на тестовом периоде Git по HTTPS блокируется, резервная попытка — архив GitHub по HTTPS/443.
- Исходники сохраняются в `$HOME/.dlv-automation-source` (вне сайта).
- В `$HOME/dlvautomation/public_html` через `rsync` копируются только статические файлы. `.git`, `.github`, `scripts`, `seo` и Markdown не публикуются.
- Скрипт создаёт минимальный `.htaccess` с `DirectoryIndex index.html` и двумя прежними 301-редиректами, если файла ещё нет; чужие файлы не удаляет.
- Сохраняет последнюю ревизию снаружи сайта, чтобы не повторять загрузку при неизменном Git.
- Техническая версия `dlv-deploy-revision.txt` доступна для проверки после DNS-переноса.

## Первый ручной тест (архив: этап первичной настройки, не повторять без причины)

В панели Timeweb → `SSH-консоль` от **основного пользователя** выполните одну команду:

```sh
mkdir -p "$HOME/dlvautomation" && curl -fsSL https://raw.githubusercontent.com/Rbastl/dlv-automation/main/scripts/timeweb_sync_from_github.sh -o "$HOME/dlvautomation/timeweb_sync_from_github.sh" && /bin/sh "$HOME/dlvautomation/timeweb_sync_from_github.sh"
```

Код и все файлы запрашиваются у публичного GitHub без каких-либо паролей.

Ожидаемый вывод: `SUCCESS: DLV public website synchronized from GitHub main.`. Должны появиться `index.html`, `sitemap.xml`, `uslugi/index.html` и остальные статические страницы в Timeweb `dlvautomation/public_html`.

Если GitHub не доступен даже по HTTPS на тестовом периоде, остановиться и не переключать DNS; проверить возможность GitHub HTTPS после окончания тестового периода вместе с поддержкой.

## Постоянная автоматизация после теста (архив: не создавать второй Cron)

**Timeweb не разрешает создавать или менять Cron-задачи на 10-дневном тестовом периоде.** После перехода на оплаченный тариф можно включить автоматическое обновление без дополнительных платных услуг.

1. Timeweb → `Crontab` → `Добавить задачу`.
2. Название: `DLV GitHub sync`.
3. Интерпретатор: `Сценарий SH`.
4. Путь до скрипта: `/dlvautomation/timeweb_sync_from_github.sh` (относительно домашней папки, выбрать файлом в UI).
5. Расписание: раз в 15 минут (в экспертных настройках: минута `*/15`, остальные `*`).
6. Задать e-mail для ошибок Cron; убедиться в первом автоматическом успешном запуске.

Когда я редактирую файлы в GitHub `main`, Timeweb сам забирает новую версию в течение 15 минут. GitHub продолжает выполнять поисковые проверки и собирать Google-статистику.

## Перед переключением основного домена (архив: DNS на Timeweb уже перенесён)

1. Проверить содержимое `public_html` и технический адрес Timeweb: главная, `/uslugi/`, вложенные URL.
2. В Timeweb → Домены и SSL → настроить сертификат на `dlvautomation.ru` и `www` согласно состоянию DNS.
3. **Только после проверки тестовой копии** сменить записи DNS в Timeweb с Netlify на актуальный IP Timeweb. Текущий Timeweb server IP со скриншота: `92.53.96.223`; подтвердить его по дашборду на момент переключения.
4. Не трогать MX, SPF, DKIM, TXT верификации Google и другие почтовые записи. Проверить, что нет конфликтующей AAAA записи IPv6.
5. Проверить HTTPS, все URL и sitemap.xml на 40 страниц; тогда прекращать использование Netlify.

## Секреты и прошлые настройки

`TIMEWEB_FTP_SERVER`, `TIMEWEB_FTP_USER`, `TIMEWEB_FTP_PASSWORD` теперь не нужны новой схеме и после успешного теста могут быть удалены владельцем из GitHub Secrets. Созданный ограниченный FTP-пользователь Timeweb можно оставить отключённым как запасной или удалить по желанию. **Не присылать пароли в чат.**

Устаревший workflow `deploy-timeweb.yml` переведён только в ручной режим и не запускается при изменениях сайта.
